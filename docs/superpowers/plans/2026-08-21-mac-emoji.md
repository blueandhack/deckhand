# Per-Mac emoji icons Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each Mac can carry a small icon, shown on the device wherever that Mac is already identified — session rows, USAGE cards, the Codex row, SETTINGS › STATUS and the session detail card.

**Architecture:** The device cannot render an emoji character (`Cozette6x13` is `0x20..0x7E`), so an icon is ARTWORK: sixteen 13x13 sprites baked into flash as an RGB565 colour plane plus a 2-bit alpha plane, blended at draw time against a backdrop passed in by the caller. The Mac sends the icon's NAME as ASCII; the device maps name to sprite index. An unknown or absent name falls back to today's text tag.

**Tech Stack:** Python 3 + headless Google Chrome for rasterising (no SVG library exists in this toolchain), Arduino ESP32 core 3.3.11 with TFT_eSPI, Node 20+ on the host, Swift/AppKit for the menu bar.

**Spec:** `docs/superpowers/specs/2026-08-21-mac-emoji-design.md`

## Global Constraints

- **The font cannot draw emoji.** `Cozette6x13` declares `0x20, 0x7E`. Never attempt to `drawString` an emoji; it renders as a blank box. Every icon is a sprite.
- **Sprites are 13x13.** A usage card's label row is `y0+6`..`y0+19`; the hero number's box starts at `y0+20` and clears from `y0+19`, spanning the full card interior. 16px would collide with that clear box.
- **Format: RGB565 colour plane + separate 2-bit alpha plane**, 338 + 43 = **381 bytes per icon**. The backdrop is passed in at draw time and never baked in — baking one in is what gives `ClawdCrab.h` its documented fringe under LIGHT.
- **Vertical rule, everywhere:** an icon's `y` is the same `y` its neighbouring text uses with `TL_DATUM`, because both are 13px. Horizontal gap between icon and text is **4px**, everywhere.
- **`pushImage` byte order:** any row buffer pushed to the screen needs `tft.setSwapBytes(true)` and a restore of the previous value, exactly as `drawLogo` does. Getting this wrong is the documented reason the crab's colours came out inverted.
- **Anything drawn on a usage card must END by `y0+101`** — the 2px border owns `+102..+103`, and `drawIfChanged` clears `fx-1, fy-1, tw+2, th+2`, so a field's CLEAR BOX is what damages a border.
- **No function signature may name `SessionInfo`, `Usage`, `HostLink`, `HostPairing`, `Theme` or `ConfirmAction`** — the Arduino build inserts generated prototypes above those declarations. Helpers take/return int indices or `const char*`.
- **Every affected surface caches on TEXT, and an icon change moves no text.** The icon id must enter: the row signature, the detail signature (**`detailSigCache` must grow from 368** — it has 19 bytes of headroom against a 349-byte worst case), the usage chrome bust, and the SETTINGS Mac row's cached string.
- **The NAME crosses the wire, never the character.** `hostEmoji: "rocket"`, ASCII only.
- **An unknown or absent name falls back to the existing text tag.** No surface may end up with neither.
- **Long commands must be backgrounded and polled**, never run as a silent foreground call: `nohup arduino-cli compile --fqbn "esp32:esp32:esp32:PartitionScheme=huge_app" firmware/deckhand_display > /tmp/c.log 2>&1 &` then `sleep 20; tail -3 /tmp/c.log`. A silent foreground compile/flash has repeatedly tripped an inactivity watchdog on this project.
- **Flash with `./flash.sh --no-compile`, NEVER a bare `arduino-cli upload`** — the supervised host re-grabs the serial port within ~1s and the upload fails on a busy port, looking like a hardware fault. **Check the compile actually SUCCEEDED before flashing:** `--no-compile` happily flashes the previous artifact, which has already caused a fix to be "verified" that was never built.
- **Device commands go through `~/.claude/deckhand-device-command`**, never a second serial connection (opening one pulses the CH340 reset line and reboots the ESP32). `TAB 0|1|2`, `PAGE 0..3`, `SCREENSHOT` (~18s, lands in `~/Deckhand-shots/`), `MULTITEST <n>` (a synthetic second Mac, `hostId feedfeed`, tag `studio`).
- **Verify on BOTH themes.** The alpha blend must be right against a card and a row backdrop in DARK and LIGHT. The theme control is SETTINGS › DISPLAY & SOUND.

### Task 1: The generator, the art, and the legibility go/no-go

**This task decides whether the feature is worth having.** Risk 1 in the spec is that a 13px emoji may be unreadable, and no amount of reasoning settles it. This task ends by LOOKING at the art.

**Files:**
- Create: `firmware/deckhand_display/emoji2c.py`
- Create: `firmware/deckhand_display/MacEmoji.h` (generated output, committed — the BDFs are not committed but generated headers are, per this repo's convention)

**Interfaces:**
- Produces: `MacEmoji.h` defining `MAC_EMOJI_SIZE` (13), `MAC_EMOJI_COUNT` (16), `MAC_EMOJI_NAMES[]` (a `const char* const` array in PROGMEM order), `MAC_EMOJI_RGB[]` (colour planes, `uint16_t`, `MAC_EMOJI_COUNT * 169`), `MAC_EMOJI_ALPHA[]` (2bpp planes, `uint8_t`, `MAC_EMOJI_COUNT * 13 * 4` — 4 bytes per 13-pixel row, the same `(size + 3) / 4` stride `blit2bpp` already assumes), and `int macEmojiIndex(const char* name)` returning -1 when unknown.

- [ ] **Step 1: Read the generator you are extending**

Run: `sed -n 1,130p firmware/deckhand_display/codex2c.py`

You are reusing its Chrome invocation and its PNG reader. Do not write a new PNG decoder: this toolchain has no `rsvg-convert`, `inkscape`, `cairosvg`, or Pillow, which is exactly why that reader exists. Note `CHROME = "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"` (verified present) and that `/System/Library/Fonts/Apple Color Emoji.ttc` is a system font, so nothing needs downloading.

- [ ] **Step 2: Write the generator**

`emoji2c.py` renders each emoji as an HTML page in headless Chrome at 128px on a transparent background, reads the PNG **with alpha** (`codex2c.py`'s reader is greyscale — extend it to keep the alpha channel, or read RGBA and carry all four), box-filters 8x8 down to 13x13, then emits:

- colour as RGB565 (`(r>>3)<<11 | (g>>2)<<5 | b>>3`), with fully transparent pixels emitted as 0 (never drawn, so their colour is irrelevant),
- alpha quantised to 2 bits (0,1,2,3) packed 4-per-byte, high bits first — the same packing `blit2bpp` unpacks with `(byte >> (6 - 2 * (x & 3))) & 3`,
- the name table, in the same order as the planes.

The set, in this order: `rocket moon star bolt fire leaf wave anchor crab laptop desktop cloud sun cat robot gear`.

Emit `int macEmojiIndex(const char* name)` as a plain linear `strcmp` loop — 16 entries, called once per payload, so a table lookup is not worth a hash.

- [ ] **Step 3: Add `--verify` and `--selftest`**

`--verify <header>` decodes the emitted header back to pixel planes and compares it, byte for byte, against a freshly rendered raster; `--selftest` corrupts one byte of the first icon's alpha plane and FAILS if `--verify` does not notice. This is the teeth-proving pattern `bdf2gfx.py --selftest` and `palette-check.mjs --selftest` already use; a checker nobody has proven can fail is decoration.

- [ ] **Step 4: Generate the header**

Run:
```bash

sleep 25; tail -5 /tmp/emoji-gen.log; wc -c MacEmoji.h.tmp
```
Expected: roughly 6.1KB of art plus source text, no errors. Move it into place only once it is non-empty (`mv MacEmoji.h.tmp MacEmoji.h`).

- [ ] **Step 5: Prove the verifier has teeth**

Run:
```bash

python3 emoji2c.py --selftest && echo "SELFTEST OK (it caught the corruption)"
```

- [ ] **Step 6: THE GO/NO-GO — look at the art**

Have the generator write a preview PNG of all 16 icons at 13x13, upscaled 8x with nearest-neighbour (so pixels stay crisp) on both a dark (`#18C4`-ish) and a light background, side by side:
```bash

```
Then READ `/tmp/emoji-preview.png` and judge each icon: can you tell what it is? Record a verdict per icon in the report.

**This is a decision point, not a formality.** If more than a few are unrecognisable, STOP and report — the spec's documented fallbacks are a smaller set of simpler shapes, or 2-bit monochrome silhouettes tinted at draw time like the spark. Do not carry unreadable art into six surfaces.

import { resolveMacEmoji, MAC_EMOJI_NAMES } from "./mac-emoji.mjs";

let failed = 0;
const eq = (got, want, what) => {
  if (got === want) return;
  console.error(`FAIL ${what}: got ${JSON.stringify(got)} want ${JSON.stringify(want)}`);
  failed++;
};

eq(MAC_EMOJI_NAMES.length, 16, "sixteen names");
eq(MAC_EMOJI_NAMES[0], "rocket", "first name is rocket, matching the header's order");

// The env var is the provisioning path and must win: a deliberately-set plist value
// cannot be silently overridden by a stray click in the menu bar.
eq(resolveMacEmoji({ env: "moon", file: "star" }), "moon", "env beats file");
eq(resolveMacEmoji({ env: "", file: "star" }), "star", "file used when env is unset");
eq(resolveMacEmoji({ env: "", file: "" }), "", "nothing set yields nothing");

// An unknown name must resolve to "" so the device falls back to the TEXT tag. Sending
// it through would leave the device with no icon and no text.
eq(resolveMacEmoji({ env: "banana", file: "" }), "", "unknown name is rejected");
eq(resolveMacEmoji({ env: "banana", file: "moon" }), "moon", "a bad env falls through to a good file");

eq(resolveMacEmoji({ env: "  moon \n", file: "" }), "moon", "whitespace trimmed");
eq(resolveMacEmoji({ env: null, file: undefined }), "", "null and undefined are safe");
// The emoji CHARACTER is never a valid value: only names cross the wire.
eq(resolveMacEmoji({ env: "\u{1F680}", file: "" }), "", "an emoji character is not a name");

console.log(failed ? `mac-emoji: ${failed} FAILED` : "mac-emoji: all checks passed");

- [ ] **Step 3: Implement the module**

Create `host/mac-emoji.mjs`:

```js
// The ONE place the Mac side knows which icon names exist. The device has its own copy
// in MacEmoji.h, generated by emoji2c.py - the two are separate languages and must be
// edited together; CLAUDE.md says so, because a name valid here and unknown there shows
// as no icon at all.
//
// Order matters only for the check script's first-name assertion; the wire carries the
// NAME, never an index, so adding to the middle of this list is safe.
export const MAC_EMOJI_NAMES = [
  "rocket", "moon", "star", "bolt", "fire", "leaf", "wave", "anchor",
  "crab", "laptop", "desktop", "cloud", "sun", "cat", "robot", "gear",
];

// env beats file: the plist is the provisioning path, and a value someone set
// deliberately must not be silently overridden by a click in the menu bar. An invalid
// value at either level is DROPPED rather than passed through, so the device falls back
// to the text tag instead of showing nothing at all.
export function resolveMacEmoji({ env, file } = {}) {
  const clean = (v) => String(v ?? "").trim().toLowerCase();
  for (const candidate of [clean(env), clean(file)]) {
    if (candidate && MAC_EMOJI_NAMES.includes(candidate)) return candidate;
  }
  return "";
}
```

- [ ] **Step 2: Implement `drawEmoji`**

Place it next to `blit2bpp` so the two blitters read together. It follows `drawLogo`'s row-at-a-time `pushImage` shape:

```cpp
// One 13x13 icon, blended against the backdrop the CALLER names - never a baked-in
// background. The same icon has to sit on a usage card, a session row and the page
// background, in two themes; ClawdCrab.h bakes its background in and that is exactly
// why it has a fringe under LIGHT.
//
// (x, y) is the TOP-LEFT corner, matching TL_DATUM text - deliberately NOT blit2bpp's
// centre-based convention, because every caller here is placing an icon beside a text
// line whose y is its top.
void drawEmoji(int id, int x, int y, uint16_t bg) {
  if (id < 0 || id >= MAC_EMOJI_COUNT) return;
  const int n = MAC_EMOJI_SIZE;
  const uint16_t* rgb = MAC_EMOJI_RGB + id * n * n;
  const uint8_t* alpha = MAC_EMOJI_ALPHA + id * n * ((n + 3) / 4);
  static const uint8_t lut[4] = { 0, 85, 170, 255 };
  bool swap = tft.getSwapBytes();
  tft.setSwapBytes(true); // row[] holds ordinary RGB565; see the drawLogo note
  uint16_t row[MAC_EMOJI_SIZE];
  for (int py = 0; py < n; py++) {
    const uint8_t* arow = alpha + py * ((n + 3) / 4);
    for (int px = 0; px < n; px++) {
      uint8_t a = (pgm_read_byte(arow + (px >> 2)) >> (6 - 2 * (px & 3))) & 3;
      row[px] = a == 0 ? bg
                       : blend565(bg, (uint16_t) pgm_read_word(rgb + py * n + px), lut[a]);
    }
    tft.pushImage(x, y + py, n, 1, row);
  }
  tft.setSwapBytes(swap);
}
```

Check `blend565`'s real argument order and meaning before trusting this call — read its definition and match it.

- [ ] **Step 1: Write the CLAUDE.md bullet**

In this file's voice — fact, then why, then what breaks if undone. It must record:

- **The font cannot draw emoji** (`Cozette6x13` is `0x20..0x7E`), so an icon is artwork and the NAME crosses the wire. Undo that and a payload carries multi-byte text into buffers and an ask sanitiser that are ASCII-oriented.
- **13x13, derived not chosen**: a usage card's label row is `y0+6`..`y0+19` because the hero's box starts at `y0+20` and clears from `y0+19`; 16px collides with that CLEAR BOX. Matching Cozette's cell height also means no surface needs its own centring arithmetic.

- **Env beats the picker**, and the menu says so rather than showing checkmarks it cannot honour.
- **`EMOJITEST`** puts all 16 on both backdrops, for the same reason `TAB`/`PAGE`/`KBTEST` exist.
